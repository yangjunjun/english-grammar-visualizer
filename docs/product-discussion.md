# 英语语法可视化应用：讨论与设计共识

整理日期：2026-10-29。本文整理本次对话中的需求、讨论结论和实现边界，不是逐字聊天记录。计划与示例不代表已经完成。

## 1. 应用目标

开发一个面向英语学习者的可视化、可交互 Web 应用，重点分析整个句子的语法结构。

核心学习方式：先看清句子的“基本骨骼”，再逐层添加或展开修饰成分，理解复杂句如何组成。学习者应能看出每一部分是什么、在句子里做什么，以及与其他部分的关系。

五种基本句型作为入门入口：

| 句型 | 结构 | 示例 |
|---|---|---|
| 主谓 | S + V | Birds fly. |
| 主谓宾 | S + V + O | I like music. |
| 主系表 | S + V + C | She is happy. |
| 主谓双宾 | S + V + O + O | He gave me a book. |
| 主谓宾补 | S + V + O + C | We call him Tom. |

五种句型是教学框架，不是对所有英语结构的穷尽分类。复杂句除了添加修饰语，还包括并列、从属和嵌套；某些补足成分也不能当作可随意删除的“血肉”。

## 2. 已确认的页面与交互要求

### 整体布局

- 左侧：可展开、折叠的多级导航。上层是语法分类，叶子是具体语法点。
- 右侧：当前语法点的说明、例句和交互式分析。
- 首版只需要几个语法示例，不要求覆盖全部语法点。
- 页面简洁，突出句子与结构；使用 CSS 变量集中调整颜色、字体、字号、间距等样式。
- 导航菜单不使用装饰图标，只使用 CSS 绘制的三角形标识折叠状态：折叠朝右，展开朝下。

### 配色与层级

同时表达两个维度：

1. **语法功能**：主语、谓语、宾语等采用固定主色。
2. **构成类型**：名词、代词、短语、从句等通过相近色和标签区分。

第二个维度称为“构成类型”更合适，因为词性、短语类别和从句不是同一层次的概念。

同一个名词短语可以作主语，也可以作宾语；其主色由当前功能决定，不能把名词短语固定归入主语。

嵌套结构还需要边框、下划线、缩进和适当减小字号等视觉区分，不仅依赖颜色。深层嵌套不应无限缩小字号，应主要通过折叠与层级表达。

### 递归分析

- 默认可以查看骨骼，再查看完整结构或逐层添加修饰。
- 点击成分查看其功能、构成类型和解释。
- 点击有内部结构的短语或从句，在下方展开分析面板。
- 连线从**父色块底边中心**连接到**子分析面板顶边中心**。
- 子面板与主句一样支持点击解释、骨骼与完整结构切换，以及继续展开。
- 各层独立保存选中、阶段与展开状态，可以单独收起。
- 原句始终按原词序呈现；分层展示不能把前置成分强行改排成 SVO。
- 已经是最简骨骼的结构应明确说明，不人为删除必要成分。

例如 `What he said surprised me.`：

- 外层：`What he said` 整体作主语，`surprised` 作谓语，`me` 作宾语。
- 内层按原序：`What` 作宾语、`he` 作主语、`said` 作谓语。
- 外框保留整个结构的主语归属，内部成分使用当前层的功能配色。

这里采用教学解释；现代语法对 `What he said` 还涉及融合关系结构的分析，不能宣称所有理论都将它归为同一类别。

## 4. 用户自定义句子与 AI 分析目标

用户希望后续能输入任意想分析的句子，由 AI 输出符合规格的 JSON，再交给统一渲染器展示。

数据与展示职责分离：

- AI 输出语法结构、解释、原句对应关系等数据。
- 前端决定颜色、字号、布局、连接箭头和交互状态。
- 预设例句与用户输入应尽量使用同一套结构与渲染逻辑。
- JSON 结构合法不等于语言学分析正确，应保留无法可靠分析或存在歧义的说明能力。

输入界面、模型调用与 JSON 接入尚未实现。

## 5. 语言学方向的讨论

讨论中借鉴了以下方向：

| 方向 | 对应用的价值 |
|---|---|
| 成分结构分析 | 表达哪些词组成短语、哪些结构可以继续展开 |
| 形式与功能区分 | 分开描述“是什么”和“在父结构中做什么” |
| 依存分析 / UD | 解释谁修饰谁、谁依附于谁，可作为扩展参考 |
| 补足语与附加语 | 避免把所有介词短语、状语等都当作可删修饰 |

相关资料及正式规范参考链接见 [语法 JSON 规范](grammar-json/README.md#2-理论依据与协议边界)。

注意：展开箭头表示组成关系，不等于依存箭头。语言学理论为分析提供依据，但不自动证明颜色、折叠与动画的教学效果。

## 7. 最新方向：借鉴编程语言 AST

用户提出可以参考编程语言 AST。讨论认可采用类似 AST 的递归节点设计，构建面向学习的英语成分树。

| AST 概念 | 本应用对应 |
|---|---|
| 程序或表达式 | 句子或从句 |
| 节点类型 | 词、短语、从句 |
| 节点在父结构中的位置 | 主语、谓语、宾语、修饰语等功能 |
| 子表达式 | 内部成分 |
| 源码位置 | 对应原句的位置 |

### 建议保留的核心字段

| 字段 | 用途 |
|---|---|
| `type` | 节点是什么：名词、短语、从句等 |
| `role` | 节点在父结构中的功能 |
| `text` | 对应原文 |
| `children` | 可递归展开的内部结构 |
| `explanation` | 可选的中文学习解释 |
| `translation` | 句子或从句的译文，具体范围待定 |
| `pattern` | 可选的句型教学标记 |

从句与主句可以共用 `type: "clause"`，通过它在父结构中的 role 区分用途。前端递归渲染，不为第二层、第三层分别写一套逻辑。

### 讨论中的简化示例

以下是设计示意，不是已经定稿的学习版 Schema，也不是当前页面可直接导入的文件。

```json
{
  "type": "clause",
  "text": "The little boy ate an apple.",
  "translation": "那个小男孩吃了一个苹果。",
  "pattern": "SVO",
  "children": [
    {
      "type": "noun_phrase",
      "role": "subject",
      "text": "The little boy",
      "children": [
        { "type": "article", "role": "determiner", "text": "The" },
        { "type": "adjective", "role": "modifier", "text": "little" },
        { "type": "noun", "role": "head", "text": "boy" }
      ]
    },
    { "type": "verb", "role": "predicate", "text": "ate" },
    {
      "type": "noun_phrase",
      "role": "object",
      "text": "an apple",
      "children": [
        { "type": "article", "role": "determiner", "text": "an" },
        { "type": "noun", "role": "head", "text": "apple" }
      ]
    }
  ]
}
```

### 骨骼字段的讨论

曾建议增加 `essential`，表示“当前层的骨骼视图是否保留此节点”。例如整个主语短语保留，内部的 little 可在该短语的骨骼视图中隐藏。

这个布尔值不能被解释为“任何语境下都不能省略”的语言学结论。字段名称、默认值，以及暂隐引导词与真实可删修饰的区别，仍需在学习版规范中明确；目前没有最终定稿。

### 与编程 AST 的区别

- 自然语言可能有歧义，不能假定永远只有唯一正确的树。第一版可以采用一种解读并附说明，复杂候选机制暂不作为必需项。
- 学习展示需要保留原文和原词序，不应丢失标点或随意重写结构。
- 上述简化示例没有单独表示句末标点，正式规格还需确定标点与原文位置的处理方式。
- AI 输出仍需基本结构与一致性约束；简化格式不等于省略正确性边界。

## 8. 建议暂缓的复杂能力

为优先服务当前学习体验，讨论建议学习版暂不强制包含：

- 独立 UD 依存树。
- 全局节点表与大量跨节点 ID 引用。
- 多套完整候选分析。
- 全量词法形态特征。
- 显式空位和复杂省略图。
- 为每个节点生成复杂、独立的教学阶段计划。

这些是简化方向，不代表已从原来的完整 Schema 删除。
